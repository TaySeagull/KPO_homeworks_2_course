## Ubiquitous Language

Для проектирования используется единый язык предметной области:

- Student - Студент, которого оценивают
- Criterion - Критерий, по которому выставляется оценка
- Rubric - Рубрикатор, содержащий набор критериев
- Evaluation - Факт выставления оценки студенту
- ScoreValue - Числовое значение оценки
- FinalScore - Рассчитанный итоговый результат

## Entity (сущности)

### Student (студент)

Сущность, представляющая студента. Имеет уникальный идентификатор, который сохраняется при изменении атрибутов. Одновременно Student является агрегатом (aggregation root), но об этом ниже в пункте "агрегаты".

Содержит:

- уникальный идентификатор, ID;

- имя, Name;

- фамилию, Surname;

- отчество, Patronymic;

- группу, Group;

- факультет, Faculty.

```go
type Student struct {

    id          string

    name        string

    surname     string

    patronymic  string

    group       string

    faculty     string

    evaluations map[string]Evaluation

}
```

### Criterion (критерий)

Сущность, определяющая параметр оценивания. Содержит название, максимальный балл и вес в итоговой оценке.

Содержит:

- уникальный идентификатор, ID;

- название, Name;

- максимальный балл, MaxScore;

- вес в итоговой оценке, Weight.

```go

type Criterion struct {

    id       string

    name     string

    maxScore MaxScore

    weight   Weight

}

```

### Evaluation (оценка)

Сущность, представляющая факт выставления оценки конкретному студенту по определённому критерию.

Содержит:

- идентификатор критерия, CriterionID;

- значение оценки, ScoreValue;

- комментарий, Comment;

- дату последнего выставления или изменения оценки, UpdatedAt.

```go

type Evaluation struct {

    criterionID string

    score       ScoreValue

    comment     string

    updatedAt   time.Time

}

```

Для одной пары Student + Criterion существует только одна актуальная Evaluation. При исправлении оценки обновляется существующая сущность, история изменений не сохраняется.

## Value Object (объекты-значения)

Объекты-значения не имеют собственной идентичности и определяются своими значениями.

### ScoreValue

```go

type ScoreValue struct {

    value int

}

```

Числовое значение оценки. Не может быть отрицательным и не может превышать максимальный балл соответствующего критерия.

### FinalScore

```go

type FinalScore struct {

    value int

}

```

Итоговый результат, полученный в результате расчёта оценок студента по критериям рубрикатора.

### Weight

```go

type Weight struct {

    value int

}

```

Вес критерия, определяющий его вклад в итоговую оценку. Хранится как целое число от 1 до 100, где 100 соответствует 100%, 50 - 50% и т. д. Сумма весов всех критериев рубрикатора должна составлять 100.

### MaxScore

```go

type MaxScore struct {

    value int

}

```

Максимально допустимое значение балла по критерию. Должно быть положительным числом.

## Агрегаты

Aggregate Root - объект, через который управляется поведение группы связанных объектов.

В проекте выделяются два основных агрегата: Student и Rubric.

### Student (Aggregate Root)

Управляет данными конкретного студента и его оценками.

Содержит:

- данные студента;

- набор сущностей Evaluation.

Предоставляет методы:

- `SetEvaluation` - выставление новой оценки или изменение существующей;

- `GetEvaluation` - получение оценки по идентификатору критерия;

- `GetEvaluations` - получение всех оценок студента.

Отвечает за соблюдение следующих инвариантов:

1. У одного студента может быть только одна актуальная оценка по одному критерию.

2. Нельзя выставить отрицательную оценку.

3. Нельзя выставить оценку выше максимального балла критерия.

4. При изменении оценки обновляются её значение, комментарий и дата последнего изменения.

### Rubric (Aggregate Root)

Управляет рубрикатором дисциплины и входящими в него критериями.

Содержит:

- набор сущностей Criterion.

```go

type Rubric struct {

    criteria map[string]Criterion

}

```

Предоставляет методы:

- `AddCriterion` - добавление нового критерия;

- `RemoveCriterion` - удаление критерия;

- `UpdateCriterion` - изменение характеристик критерия;

- `GetCriterion` - получение критерия по идентификатору;

- `GetCriteria` - получение всех критериев.

Отвечает за соблюдение следующих инвариантов:

1. Нельзя добавить несколько критериев с одинаковым идентификатором.

2. Максимальный балл критерия должен быть положительным.

3. Вес критерия должен быть допустимым.

4. Сумма весов критериев должна составлять 100 при завершении настройки рубрикатора и перед расчётом итоговой оценки.

## Domain Service

Domain Service используется для реализации бизнес-логики, которая не принадлежит одной конкретной сущности или агрегату.

В проекте Domain Service отвечает за расчёт итоговой оценки студента на основании его оценок и критериев рубрикатора.

Предоставляет метод:

- `CalculateFinalScore` - расчёт итоговой оценки студента.

Метод принимает список Evaluation и список Criterion, после чего возвращает FinalScore.

Входные данные:

- []Evaluation - список выставленных студенту оценок;

- []Criterion - список критериев рубрикатора.

Результат:

- FinalScore - итоговая оценка по десятибалльной шкале;

При расчёте соблюдаются следующие правила:

1. Рубрикатор должен содержать корректный набор критериев.

2. Сумма весов критериев должна составлять 100%.

3. Для каждого критерия учитывается соответствующая оценка студента.

4. Если оценка отсутствует, её значение принимается равным нулю.

5. Итоговая оценка должна находиться в диапазоне от 0 до 10.

6. Полученный результат округляется математически до целого числа.

Для каждого критерия определяется выставленная оценка. Если оценка отсутствует, она учитывается как ноль.

Оценка нормализуется относительно максимального балла критерия и умножается на его вес. Поскольку вес хранится в процентах, при расчёте он делится на 100.

Результаты суммируются, после чего итог округляется математически до целого числа.

Формула расчёта:

FinalScore = round(10 * Sum((ScoreValue / MaxScore) * (Weight / 100)))

## Repository (репозитории)

Repository - абстракция для получения и сохранения агрегатов. Позволяет отделить доменную модель от конкретного способа хранения данных.

В проекте используются два репозитория, соответствующие двум агрегатам.

### StudentRepository

Отвечает за получение и сохранение агрегатов Student.

Предоставляет методы:

- `GetByID` - получение студента по идентификатору;

- `GetAll` - получение всех студентов;

- `Save` - сохранение нового или изменённого студента;

- `ExistsByID` - проверка существования студента с указанным идентификатором;

- `ExistsEvaluationForCriterion` - проверка наличия хотя бы одной оценки по указанному критерию среди всех студентов.

StudentRepository работает с агрегатом Student целиком. Отдельный репозиторий для Evaluation не создаётся, поскольку Evaluation является частью агрегата Student.

### RubricRepository

Отвечает за получение и сохранение агрегата Rubric.

Предоставляет методы:

- `Get` - получение рубрикатора;

- `Save` - сохранение нового или изменённого рубрикатора.

RubricRepository работает с агрегатом Rubric целиком. Отдельный репозиторий для Criterion не создаётся, поскольку Criterion является частью агрегата Rubric.

### Application Services и сценарии использования

Application Services координируют работу репозиториев. Их задача - получить необходимые агрегаты, вызвать доменные методы, проверить межагрегатные ограничения и сохранить результат.

В приложении выделены следующие сервисы:

#### StudentService

- AddStudent - проверяет, что студент с таким ID ещё не существует, создаёт Student через доменную фабрику и сохраняет его;

- GetStudent - получает студента по ID;

- GetAllStudents - получает список всех студентов.

#### RubricService

- AddCriterion - создаёт Criterion и добавляет его в Rubric;

- UpdateCriterion - проверяет существование критерия и отсутствие оценок по нему у всех студентов, после чего обновляет критерий;

- RemoveCriterion - проверяет существование критерия и отсутствие оценок по нему у всех студентов, после чего удаляет критерий;

- GetRubric - получает текущий рубрикатор.

#### EvaluationService

- SetEvaluation - получает студента и рубрикатор, проверяет наличие критерия в рубрикаторе, создаёт ScoreValue, передаёт оценку агрегату Student и сохраняет обновлённый агрегат.

Максимальный балл берётся из Criterion, поэтому пользователь не может произвольно указать его при выставлении оценки.

#### ScoreService

- CalculateStudentScore - получает студента и рубрикатор, передаёт список оценок студента и список критериев в Domain Service CalculateFinalScore и возвращает FinalScore.


## Инварианты доменной модели

1. Оценка не может быть отрицательной.

2. Оценка не может превышать максимальный балл критерия.

3. Оценку можно выставить только по существующему критерию рубрикатора.

4. У одного студента может быть только одна актуальная оценка по одному критерию.

5. Отсутствующая оценка учитывается как ноль при расчёте итога.

6. Критерий нельзя изменять после выставления по нему хотя бы одной оценки.

7. Критерий нельзя удалить, если по нему существует хотя бы одна оценка.

8. Сумма весов критериев должна составлять 100.

9. Итог рассчитывается на основании текущих оценок и рубрикатора.

## Распределение ответственности

- Student отвечает за данные студента и корректность его оценок.

- Evaluation представляет факт выставления оценки и хранит её актуальное состояние.

- Criterion отвечает за корректность собственных характеристик.

- Rubric отвечает за управление критериями и соблюдение ограничений всего рубрикатора.

- Application Service организует взаимодействие агрегатов, проверяет межагрегатные ограничения, загружает необходимые данные и сохраняет изменения.

- Domain Service содержит бизнес-логику, которая не принадлежит одной конкретной сущности. В частности, отвечает за расчёт итоговой оценки студента на основании его оценок и критериев рубрикатора.

## Архитектура приложения

Для построения приложения используется Clean Architecture. Она позволяет разделить бизнес-логику, сценарии использования, адаптеры и инфраструктуру.

Основной принцип архитектуры - зависимости направлены внутрь. Внутренние слои не зависят от внешних технических деталей.

### Domain (Entities)

Внутренний слой, содержащий доменную модель и бизнес-правила предметной области.

Содержит:

- доменные сущности Student, Evaluation, Rubric, Criterion;

- объекты-значения ScoreValue, FinalScore, Weight, MaxScore;

- Domain Service для расчёта итоговой оценки.

Отвечает за состояние доменных объектов, соблюдение инвариантов и выполнение бизнес-операций.

### Application (Use Cases)

Слой сценариев использования приложения.

Содержит:

- Application Services;

- интерфейсы репозиториев StudentRepository и RubricRepository;

- StudentService, RubricService, EvaluationService и ScoreService;

- сценарии добавления и получения студентов, управления критериями, выставления оценок и расчёта итоговой оценки.

Отвечает за координацию доменных объектов, получение и сохранение агрегатов, выполнение пользовательских сценариев.

### Interface Adapters

Слой адаптеров, обеспечивающих взаимодействие внутренней логики с внешним миром.

В проекте используется консольный интерфейс, который отвечает за получение пользовательского ввода, преобразование данных в запросы Use Cases и отображение результатов.

### Infrastructure

Внешний слой, содержащий технические реализации.

Для хранения данных используется формат JSON.

Данные разделены на два файла:

- `students.json` - хранение агрегатов Student вместе с входящими в них Evaluation;

- `rubric.json` - хранение агрегата Rubric вместе с входящими в него Criterion.

Содержит:

- реализации репозиториев;

- работу с JSON-файлами;

- механизмы чтения, записи и сериализации данных.

### Dependency Injection

Для внедрения зависимостей используется готовая библиотека `github.com/samber/do/v2` (версия 2.1.0).

DI-контейнер отвечает за создание и регистрацию компонентов приложения, разрешение их зависимостей и передачу необходимых объектов через конструкторы.

## Использованные паттерны GoF

В проекте используются три паттерна GoF, относящиеся к разным категориям: порождающие, структурные и поведенческие.

### Factory (Порождающий паттерн)

В качестве простого варианта паттерна Factory используются доменные функции-конструкторы:

- `NewStudent` — создание студента;
- `NewCriterion` — создание критерия;
- `NewEvaluation` — создание оценки;
- `NewRubric` — создание рубрикатора.

Функции-конструкторы инкапсулируют создание доменных объектов и проверку исходных данных.

Например, `NewStudent` проверяет обязательные поля студента, а `NewCriterion` проверяет корректность идентификатора, названия, максимального балла и веса.

Таким образом, создание объектов централизовано, а некорректные экземпляры не допускаются в доменную модель.

### Facade (Структурный паттерн)

Для упрощения взаимодействия с прикладным слоем используется паттерн Facade.

В проекте его реализует `ApplicationFacade`.

Фасад предоставляет единую точку входа для выполнения основных операций приложения:

- добавление и получение студентов;
- добавление, изменение и удаление критериев;
- выставление оценок;
- расчёт итоговой оценки;
- экспорт результатов.

Внутри фасад делегирует выполнение операций соответствующим Application Services: `StudentService`, `RubricService`, `EvaluationService`, `ScoreService` и `ExportService`.

Фасад скрывает внутреннюю организацию прикладного слоя и упрощает использование приложения.

### Strategy (Поведенческий паттерн)

Для организации расчёта итоговой оценки используется паттерн Strategy.

В проекте определён интерфейс `ScoreCalculationStrategy`, который задаёт общий контракт для алгоритмов расчёта:

`Calculate(evaluations, criteria)`

Текущая реализация стратегии — `WeightedScoreStrategy`. Она выполняет расчёт итоговой оценки с использованием взвешенного среднего и делегирует вычисление доменной функции `CalculateFinalScore`.

Паттерн Strategy отделяет алгоритм расчёта от сценария использования и позволяет расширять приложение.

## Экспорт данных

Для экспорта итоговых оценок используется отдельный прикладной сервис `ExportService` и интерфейс `FinalScoreExporter`.

Интерфейс определяет операцию экспорта данных студента и его итоговой оценки в указанное место назначения.

В проекте реализован адаптер `CSVExporter`, который преобразует полученные данные в CSV-формат и сохраняет их в файл.

Для передачи информации между прикладным сервисом и экспортёром используется структура `ScoreExportData`. Она содержит:

- ID студента;
- имя, фамилию и отчество;
- группу;
- факультет;
- итоговую оценку.

При необходимости CSV-экспортёр можно заменить другой реализацией, не изменяя прикладной сервис.

изменения и удаления критериев, по которым уже существуют оценки;
- корректность расчёта итоговой оценки;

- ошибки при работе с репозиториями;
- сохранение и загрузка данных в формате JSON;
